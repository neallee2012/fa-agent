# Agent 回合與耐久行為控制分工

狀態：accepted（規格方向，非部署授權）｜決策日期：2026-09-15。

**2026-10-01 依 [ADR-0006](0006-team-trust-boundary-grokbot-mode.md) 縮減：** 入口接單、穩定 request ID 去重、原回條、交付回條與回合結束時的 CAS 保存全部保留；「跨程序的工作歸屬與批准由 FA 每一步核對」縮減為 ADR-0006 的 4 件事（入口、存檔、跨 VM 傳話、組織資源），其他 Hosted 每步回 API 的權威核對移除。回合中撤權於下一回合入口生效。下文原文保留為當時紀錄。

**2026-10-06 依 [ADR-0005](0005-long-running-conversation-worker.md) 調整 native 完成證據（CODE/offline，未部署）：** native 回合不再以「SDK 正常停止」作為保存前提。改為：SDK idle 完成、checkpoint 與回覆已依原 CAS 保存，下一回合只在拿到的已發布 checkpoint 正是 release 快照、且 files 之後沒變時才沿用同一個 SDK；不符就照舊停程序並從 checkpoint 還原。接單、request ID 去重、UNKNOWN 不重送、回條與 CAS 保存不變。

## 2026-09-21 補充決策：SDK-first，先復用再補缺口

使用者明確要求SDK能處理的工作以SDK為主，SDK不能處理的才考慮自建FA整合層。
因此SDK是agent回合、工具、session及runtime生命週期的主要Implementation；
FA不再以「耐久控制」為理由，複製SDK已有的對話權威、工具循環或一般程序框架。
雲端計算與身份同樣優先用平台能力；FA只補共用業務預算、Team權限、
跨入口工作歸屬、必要外部效果去重及成果／通道回條等已確認的缺口。

取捨是接受固定SDK版本的正式Interface及限制，降低自建層的維護、測試與狀態交錯成本；
不是取消業務授權、未知效果保存或資料保護。每個新自建Module須先有官方能力差額的依據，
既有重複Implementation逐步由SDK取代，而不是再包一層。
此決策不追認既有程式已精簡，也不允許倒改已持久歷史。
責任表及實作要求以[SDK-first規格修訂](../FA-AGENT-BEHAVIOR-SPEC.md#2026-09-21-實作原則修訂sdk-firstfa只補已確認的缺口)為準。

## 2026-09-20 補充決策：移除全局短窗口

使用者明確取消全局短時測試窗口，改為每工作執行額度及共用累計預算。
保留本ADR的耐久工作／交付分工，但不再用同一短期操作批准的到期時間，
連帶關閉正常接單、結果查讀與收件。
一次部署或遷移的有限操作權，與安裝後的常態使用政策分開。

這個取捨讓介面與結果可以持續使用，代價是必須把每work的時間／次數、
共用費用預留與目前讀取權分別落實，而不是依賴整場倒數粗略收尾。
不能以遠期日期、自動續期、取消身份／撤銷／去重來代替；已發布或已持久的舊期限、
code pin、回條及unknown仍是原歷史，沒有因此變成新效果的授權。
首輪採web-first，Teams整合延後；規範與必要反例集中於
[規格修訂](../FA-AGENT-BEHAVIOR-SPEC.md#2026-09-20-使用流程修訂每筆工作與共用預算不設全局短窗口)。
這裡記錄使用者的新設計決策，不代表程式或原生驗收已完成。

## 原2026-09-15決策

使用者要求將 Grok 對標提案升格為規格，並明確以正在進行的 M4 為基準。FA 採 **Hosted Agent Harness＋FA 耐久控制＋平台／工具執行端**：回合、context 與工具 hooks 靠近既有 Copilot SDK，跨程序的工作歸屬、批准、恢復及交付責任由 FA 持久管理。這補上「模型已結束但使用者仍未收到結果」與「兩端各自恢復同一工作」的缺口，不重造已驗的 M2／M3。

## 取捨與範圍

- 只改 prompt 無法保證保存、授權或交付；所有控制只放 Hosted process 又無法保證 process 消失後的接續，因此不採這兩種做法作為完整方案。
- 不將每個即時 hook 都變成遠端模型審核；普通排程、批准核對與去重由程式處理，保留 SDK 原生能力與現有 Adapter。
- 承接 [ADR-0002](0002-shared-context-without-file-share.md)／[ADR-0003](0003-hosted-environment-continuity.md)，不新增共享 mount、固定 VM、額外執行槽或預設 Temporal。
- 以 `f097fa687b0e331879e1d3c8d3b5d259b96b46e1` 的 M2／M3 為已發布基準；M2 UI 缺口、M3 歷史 FAIL／unknown 不改寫。已批准 M4 五案先按原範圍完成，新增行為放在其後。

## 後果

工作執行、外部操作與最終交付採不同狀態；明確記錄 execution owner／epoch 與每次有效批准。保存、通道接受、client 接收、UI 顯示及人類已讀分開，不能用 success／nonce 宣稱任意外部 exactly-once。

v1.1 審核整合明定：持久接單與共用批准各有不可分裂的提交集合；授權生效與撤銷共用序列化權威，但外部效果不在同一交易。先固定新入口所需的儲存／基本 consumer，之後再擴背景，不用待選型掩蓋啟用依賴，也不為單槽首切片先做滿四槽。細節與裁決只在規格維護。

v1.2 追加三項 P1 最低契約：非冪等重試需終局未生效，批准綁定 executor 真正消費的內容／版本，必要材料引用與 GC 排除競態。無對應保證的能力不啟用；首切片可停用相關自動回收，不因此選定新儲存產品或另建 ADR。控制事件容量、父子讓槽與完整 PASS 規則等 P2 仍開放。
